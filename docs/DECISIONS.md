# Decision records

Significant technical decisions, newest last. Each records the context, the decision and its consequences. Supersede a decision with a new entry rather than editing history.

## D-001 — Stack: Tauri 2, React, TypeScript, Rust, SQLite (2026-10-22)

**Context.** The workspace was empty; the specification prefers Tauri + React + TypeScript + Rust + SQLite + npm.
**Decision.** Use the preferred stack. Vite 8 builds the frontend; CSS Modules plus CSS variables provide styling.
**Consequences.** Small native binaries, a Rust backend that can later host capture adapters, and a familiar web UI toolchain. Requires the MSVC toolchain and WebView2 on Windows.

## D-002 — Stable Tauri 2, not Tauri 3 alpha

**Context.** crates.io lists `tauri 3.0.0-alpha` as latest; the CLI and API packages are on stable 2.12.
**Decision.** Pin to Tauri 2 (crate 2.12.x, CLI/API 2.12.x).
**Consequences.** Stable APIs and plugins. Revisit when Tauri 3 is released as stable.

## D-003 — TypeScript pinned to 6.0

**Context.** TypeScript 7.0 is `latest`, but `typescript-eslint` 8.72 supports `<6.1.0`. The official Tauri template pins `~6.0.3`.
**Decision.** Pin `typescript ~6.0.3`.
**Consequences.** Linting works; upgrade when typescript-eslint supports TS 7.

## D-004 — Data access in Rust with rusqlite (bundled), not tauri-plugin-sql

**Context.** The specification asks to keep capture, storage, review, generation, export and UI responsibilities separate.
**Decision.** The backend owns SQLite through `rusqlite` with bundled SQLite. The UI calls typed commands (`src/lib/api`) and never issues SQL.
**Consequences.** Validation and invariants live in one place and are unit-tested without the app. Every SQLite installation behaves identically. Adding a feature means adding a command.

## D-005 — Forward-only migrations with `PRAGMA user_version`, backups and newer-version refusal

**Decision.** Ordered migrations in Rust, each in a transaction with the version bump; copy the database with `VACUUM INTO` before upgrading an existing workspace; refuse to open databases from newer versions.
**Consequences.** Upgrades are atomic and recoverable; a downgrade can never silently damage data.

## D-006 — Identifier and timestamp formats

**Decision.** UUIDv7 text identifiers; fixed-width RFC 3339 UTC timestamps with milliseconds, generated by the backend.
**Consequences.** Stable, globally unique IDs that sort roughly by creation time; timestamps that sort lexically and parse everywhere. Display converts to local time.

## D-007 — Enum validation in Rust; structural constraints in SQL

**Context.** Status vocabularies will grow (for example new session states with capture).
**Decision.** Enumerations are Rust types (`text_enum!`) — the single source of truth — while SQL enforces types (`STRICT`), non-empty names, lengths, JSON validity and references.
**Consequences.** Adding a value does not require rebuilding tables; unknown values read from disk fail loudly rather than being misreported.

## D-008 — A workspace is one local data directory

**Context.** The specification asks for a workspace selector but lists no Workspace entity.
**Decision.** A workspace is a directory containing the database and managed folders. This build supports one workspace with a user-editable name; `DEVTRACE_DATA_DIR` selects another directory (used by tests). Adding workspaces is shown in the menu as planned, not faked.
**Consequences.** Simple backup (copy the folder) and a clear path to multiple workspaces later.

## D-009 — Dedicated `change_records` entity with an evidence level

**Context.** Change History must keep observed activity, declared changes and verified outcomes distinct, and must not treat every captured event as a configuration change.
**Decision.** Store changes in their own table with `assertion` = `observed` | `declared` | `verified` and an `approval_state`, linked optionally to a project and source session.
**Consequences.** The distinction is explicit in data and UI. Events will link to change records rather than being reinterpreted as changes.

## D-010 — Incremental schema; `playbook_sessions` for traceability

**Decision.** Schema v1 creates only the tables Milestone 1 screens read or write (settings, projects, sessions, playbooks, playbook_sessions, change_records). Events, attachments, review decisions and revisions arrive with the milestones that implement them. Playbook ↔ session traceability is many-to-many.
**Consequences.** No speculative tables; the migration path is exercised early.

## D-011 — Centralized design tokens, enforced

**Decision.** All design values live in `src/styles/tokens.css`. `scripts/check-tokens.mjs` (run by `npm run lint`) rejects literal colors and radii elsewhere.
**Consequences.** Themes are a single attribute switch; consistency is verified automatically.

## D-012 — Accessible accent variants

**Context.** White text on the specification accents is below WCAG AA (#007AFF ≈ 4.0:1, #0A84FF ≈ 3.6:1).
**Decision.** Keep the specification accents for indicators, focus rings and selection. Filled buttons use `--color-accent-fill` #0071E3 (≈ 4.7:1); accent-colored text uses #0066CC (light) and #409CFF (dark). Status uses icon + text, never color alone.
**Consequences.** The brand color is preserved where it is decorative or non-text, and text meets AA.

## D-013 — Native window decorations, synced theme, hidden-until-painted window

**Decision.** Keep the native title bar for reliability and accessibility (snap layouts, system menus); sync its theme with `window.setTheme`. Start the window hidden; an external `boot-theme.js` applies a cached theme before React renders; show the window after the first frame, with a Rust fallback after 4 s.
**Consequences.** No white flash in dark mode and no custom window controls to maintain. The localStorage cache is only a boot hint; SQLite remains authoritative.

## D-014 — Hash-based routing

**Decision.** React Router `HashRouter`.
**Consequences.** Works with Tauri's asset protocol without server rewrites; back/forward and mouse navigation buttons work; URLs encode selection (for example `/projects/:id`).

## D-015 — Unavailable features are explained, never faked

**Decision.** Controls for unimplemented features render `aria-disabled` with a reason (tooltip and accessible description) from `lib/availability.ts`. The capture status always reads "Not recording". Empty states describe what will appear and offer real next actions only.
**Consequences.** No false success states. Each milestone flips the corresponding availability entry.

## D-016 — Native `<dialog>` and `<select>`

**Decision.** Use the browser's modal dialog (focus trap, inert background, Escape, top layer) and native selects. Backdrop clicks do not close dialogs, to protect unsaved input.
**Consequences.** Robust accessibility with little custom code.

## D-017 — Least-privilege webview

**Decision.** The capability grants only `core:default` and window show/focus/theme. Revealing the workspace folder is a Rust command restricted to the workspace path. The CSP forbids external connections and inline scripts. No telemetry.
**Consequences.** A compromised or buggy UI cannot read arbitrary files, run programs or send data out. New capabilities must be added deliberately.

## D-018 — Degraded mode when storage fails

**Decision.** If the database cannot be opened, the app starts anyway and shows a full-window explanation with the error and data location.
**Consequences.** Users get an actionable message instead of a silent crash (release builds have no console).

## D-019 — Project deletion preserves related records

**Decision.** `ON DELETE SET NULL` for sessions, playbooks and changes; the confirmation dialog states how many records will become unassigned.
**Consequences.** Removing an organizational container never destroys evidence.

## D-020 — End-to-end tests drive the real binary through WebView2's DevTools protocol

**Decision.** `scripts/e2e-smoke.mjs` launches the built app with an isolated workspace and WebView2 profile (`DEVTRACE_DATA_DIR`, `WEBVIEW2_USER_DATA_FOLDER`) and connects with `playwright-core` (no browser download).
**Consequences.** Tests exercise the real Rust backend, SQLite and webview, including restarts. Windows-only for now.

## D-021 — Outline icon set

**Decision.** `lucide-react`, rendered through one `Icon` wrapper (16 px, 1.8 stroke, decorative by default).
**Consequences.** Consistent outline icons, tree-shaken bundle.

## D-022 — Version control deferred

**Context.** Git is not installed on the development machine; installing system software requires the user's consent.
**Decision.** Provide `.gitignore` (excluding local databases and evidence) and `.gitattributes`; leave `git init` to the user.

## D-023 — Images enter as bytes; no file paths cross the IPC boundary (2026-10-23)

**Context.** Milestone 2 needs user-provided screenshots before native capture exists. Granting the webview file-system or dialog permissions, or accepting paths from it, would widen what a buggy or compromised UI could read.
**Decision.** The webview reads images selected in the browser's own file chooser, pasted, or dropped, and sends their bytes as the raw body of one IPC command (`import_image`); metadata travels in headers (text percent-encoded). The backend never accepts a path from the UI and the capability set is unchanged.
**Consequences.** The UI can only hand over content the user explicitly chose. Large files are copied through IPC (bounded by the 25 MB limit). Native capture (Milestone 3) will write files directly in Rust.

## D-024 — Image type from content, with explicit limits

**Decision.** Accept only PNG, JPEG, GIF and WebP, detected from signatures (not names or MIME types claimed by the webview); read dimensions from headers without decoding pixels (`imagesize`, only these four parsers compiled in); limit files to 25 MB and 20 000 px per side; store a SHA-256 digest.
**Consequences.** Disguised files are rejected with a clear message before anything is written. Pixel data is not validated beyond headers; the webview decodes images only for display, and they are served with `nosniff`.

## D-025 — Managed attachment storage

**Decision.** Files live at `attachments/<session_id>/<attachment_id>.<ext>`; rows store only that relative path. Writes are atomic (temporary file, `sync_all`, rename, never overwrite). Inspection, hashing and writing happen without holding the database lock; the rows are recorded afterwards in one transaction that re-checks the target, and the file is removed if that fails. Every stored path is resolved through a containment check that accepts only plain names.
**Consequences.** A crash cannot leave partial files under final names; a damaged or edited database cannot point the app outside the attachments folder; slow disks do not block other commands. A crash between writing and recording can leave an unreferenced file (see D-029).

## D-026 — Evidence served by an id-based URI scheme

**Decision.** A custom asynchronous `evidence` scheme serves `evidence://localhost/<attachment-id>` (`http://evidence.localhost/…` on Windows). The id is looked up in the database; only GET/HEAD and the four image types are served, with `nosniff` and `no-store`. The CSP allows images from this scheme only (in addition to the app itself and `data:`/`blob:`); the built-in `asset` protocol is not enabled.
**Consequences.** The UI never learns file locations, deleted attachments stop resolving immediately, and evidence is not duplicated into the webview's disk cache.

## D-027 — Session lifecycle in Milestone 2

**Decision.** Sessions are `draft` or `completed`. Completing requires at least one event, records `ended_at` and makes events and attachments read-only until the session is reopened (enforced in Rust; the UI explains it). Notes and details stay editable. `recording` and `paused` remain reserved for capture and are rejected by the command.
**Consequences.** "Completed" means documentation is finished and evidence is stable for review (Milestone 4). Review state is not changed by reopening in this milestone; Milestone 4 decides how reopening affects review.

## D-028 — Event types and provenance

**Decision.** Manual event types are `step`, `note` and `command`; `screenshot` events are created only from an image. Every event and attachment records its `source` (`manual`, `file`, `clipboard`, `capture` reserved). The type never changes after creation. New events are appended (`position`); reordering waits for review. `review_status` is `pending` only; review decisions are Milestone 4. Commands are stored as text and never executed; the UI offers copy only.
**Consequences.** User-authored and user-supplied content stays distinguishable from recorded facts, which later playbook generation needs (never presenting assumptions as evidence).

## D-029 — Deletion removes rows first, then files, and reports failures

**Decision.** Session, event and attachment deletes run in a transaction while holding the database lock; files are removed afterwards and the result reports removed, missing and failed files, which the UI surfaces. Session deletion also removes the session's attachment folder (including leftover temporary files). DevTrace does not sweep unknown or orphaned files at startup.
**Consequences.** Data is never left half-deleted in the database, and the user learns when a file could not be removed (for example, held open by another program). Automatic orphan cleanup was rejected because restoring a database backup would make valid files look orphaned.

## D-030 — Autosaved session notes

**Decision.** Notes save 800 ms after typing stops, on blur and on unmount; saves never overlap and a change made during a save is saved right after it. The indicator shows "Saving…" whenever the text differs from the last stored value and keeps an error with Retry until a save succeeds; a failure after leaving the page raises a notification. The inspector keeps both tab panels mounted so switching tabs cannot reload stale notes over unsaved text.
**Consequences.** No explicit Save button and no silent data loss; at most the last 800 ms of typing are at risk if the window is closed abruptly.

## D-031 — Native drag and drop disabled on the window

**Decision.** `dragDropEnabled: false` so dropped files reach the page as HTML5 events with their contents; a global handler prevents the webview from navigating to a file dropped outside a drop zone and shows a "not allowed" cursor there.
**Consequences.** Drops work like paste and the file chooser (bytes only, D-023). Tauri's native drag-drop events are not used.

## D-032 — Paste and drop create new screenshot steps

**Decision.** Pasting (Ctrl+V outside text fields and dialogs) or dropping images always creates a new screenshot step per image, named after the file (or "Pasted screenshot"). Attaching an image to an existing step is an explicit action ("Attach screenshot…").
**Consequences.** Predictable behavior that never silently changes an existing step; titles can be edited afterwards.

## D-033 — Native capture with `xcap`, claimed for Windows only (Milestone 3)

**Context.** Capture needs display and single-window screenshots without a browser permission model. Candidates: `xcap` (GDI/WGC on Windows, also macOS and Linux), `screenshots` (unmaintained), or raw Win32.
**Decision.** Use `xcap` 0.9 with its default Windows backend: GDI `BitBlt` for displays and `PrintWindow` with `PW_RENDERFULLCONTENT` for windows (works for covered windows and most GPU-rendered apps). Capture runs on a blocking worker thread. `screen::SUPPORTED` is true only on Windows, where it was implemented and tested; other platforms report capture as unavailable with an explanation instead of claiming support.
**Consequences.** One small dependency covers both target kinds. Minimized windows are not listed (they cannot be captured). Protected content and some exclusive-fullscreen apps capture as black; such images are rejected (D-038). Windows refuses screen reads while the screen is locked, the session is disconnected, or the process runs on a desktop that is not shown; the error says so.

## D-034 — Capture is user-triggered; no input monitoring

**Decision.** A screenshot is taken only when the user presses Capture now, the global capture shortcut, or the tray menu item during a capture they started. DevTrace installs no keyboard or mouse hooks and records no keystrokes, clicks or typed text. Automatic capture (Milestone 8) will be based on visible screen changes, opt-in and clearly labeled, not on monitoring input.
**Consequences.** Nothing is recorded behind the user's back, and the privacy statement stays simple and verifiable. "Click detection" is not offered and not claimed.

## D-035 — Visible capture state and self-exclusion

**Decision.** While a capture is active, its state is shown in the sidebar (Recording/Paused with count), the capture bar (state, elapsed time, count) and a tray icon whose status dot (red recording, amber paused) is drawn at runtime; the tray menu offers Capture now, Pause/Resume, Stop and Show DevTrace. DevTrace's main window is excluded from screen capture with `set_content_protected(true)` (`WDA_EXCLUDEFROMCAPTURE`) only while recording, so screenshots show the work rather than DevTrace. Tray icons are removed on the main thread.
**Consequences.** The user always knows when capture is possible, even with DevTrace in the background. While recording, DevTrace is also hidden from other screen-sharing tools; it becomes visible to them again when the capture stops.

## D-036 — Global capture shortcut: fixed choices, registered only while recording

**Decision.** The shortcut is chosen from a fixed list (`Ctrl+Alt+Shift+S` default, `Ctrl+Shift+F9`, `Ctrl+Alt+F10`, `Pause`), validated in Rust, registered from Rust through `tauri-plugin-global-shortcut` when a capture starts and unregistered when it stops. The webview has no shortcut permission. If registration fails (another application owns the combination), the capture still runs and the capture workspace explains how to proceed; the tray menu shows the shortcut only when it is active. Changing the setting during a capture re-registers immediately.
**Consequences.** DevTrace never holds a system-wide key combination while idle, and a conflict never blocks capturing.

## D-037 — Capture lifecycle and recovery

**Decision.** A capture targets one draft session: draft → recording ↔ paused → draft. Stopping returns the session to draft; completing stays an explicit user action after review. While a capture is active the session cannot be completed, reopened or deleted. The live state lives in `CaptureController` (memory); sessions found recording or paused at startup (the app was killed) return to draft, and a normal exit ends the capture first. Screenshots never overlap; one finishing after Stop is still stored in its session.
**Consequences.** No session is ever stuck in "Recording" after a crash, and the database never claims a capture that is not running.

## D-038 — Captured images: opaque PNG, black images refused, provenance recorded

**Decision.** Captures are converted to RGB (alpha dropped) and encoded as PNG with fast compression, then stored through the same import pipeline as user-supplied images (`source = capture`). A completely black result is refused with an explanation instead of being stored as evidence. The event records metadata `{ capture: { trigger, capturedAt, target: { kind, title, appName, width, height } } }`, shown in the inspector. Image crates are compiled with optimizations even in development builds.
**Consequences.** Every captured screenshot says how and of what it was taken. Window titles can contain sensitive text; they are stored locally like any evidence and can be edited in the step title.

## D-039 — Annotations are non-destructive

**Decision.** Highlight boxes are stored as JSON on the attachment (`annotations_json`, image pixel coordinates, optional label, at most 50, validated against the image size) and drawn over the image; the file is never modified. Permanent redaction is a separate, destructive operation (Milestone 4).
**Consequences.** Annotations can be edited or removed at any time and never alter evidence. Completed sessions lock annotations like other evidence.

## D-040 — Command results are also published in-app

**Decision.** Capture state and captured screenshots arrive as backend events (`capture-status`, `capture-captured`), which also cover the shortcut and tray. Results of the user's own commands are published to the same subscribers through an in-app channel (`publishLocal`), and handlers ignore duplicates.
**Consequences.** The interface updates immediately after a click, keeps working when backend events are unavailable (tests, plain browser), and background captures still appear.

## D-041 — Capture end-to-end checks adapt to the environment

**Context.** Automation sandboxes may run the app on a Windows desktop that is not shown, where screen pixels cannot be read and injected keys would reach the user's real desktop.
**Decision.** The E2E test probes whether the screen is readable. If it is, display screenshots are decoded and checked; otherwise it verifies that the failure is explained and nothing is stored, and reports the pixel check as skipped. Window capture is always verified against a test window with known content. Key presses are injected only with `--interactive`.
**Consequences.** The default run never touches the user's desktop and never reports an unverified check as passed; `npm run test:e2e -- --interactive` verifies display capture and the shortcut on a real desktop.

## D-042 — Review decisions per step, audited, independent of completion (Milestone 4)

**Decision.** Every step gets a review status: `pending`, `approved`, `rejected` (wrong or misleading) or `excluded` (irrelevant). Each change appends a row to `review_decisions` with the previous and new status, an optional comment and the reviewer (the author name from Settings). Re-applying the same status without a comment records nothing. Decisions do not change evidence, so they remain possible after a session is completed; reordering and redaction change content and require an open session.
**Consequences.** Only approved steps will feed playbooks (Milestone 5); rejected and excluded steps stay in the session for traceability but never reach documentation. The audit trail survives step deletion (`event_id` becomes null, the history shows "deleted step").

## D-043 — Session review state follows the decisions

**Decision.** `review_state` moves from `unreviewed` to `in_review` on the first review action. "Mark reviewed" is allowed only when the session has steps and none is pending, and is recorded as a decision. A step set back to pending, or a new step added later, returns a reviewed session to `in_review`; a finished review can also be reopened explicitly.
**Consequences.** "Reviewed" always means every current step has a decision; the Overview's awaiting-review list stays truthful.

## D-044 — Redaction is destructive, confirmed and verifiable

**Decision.** Redaction burns opaque black rectangles into the pixels (decoded with allocation limits, first frame for animations), writes a new PNG (`<attachment>-redacted-<id>.png`), switches the attachment row to it in a transaction (new SHA-256, size, `redacted_at`), and deletes the original file. Rectangles must lie inside the image (at most 50 per operation). The user marks areas on the screenshot, sees how many are marked, and must confirm a dialog that states the original is deleted. If the original cannot be deleted, the user is told where it remains. Annotations are kept.
**Consequences.** Hidden content cannot be recovered from DevTrace. GIF and WebP screenshots become PNG after redaction. The decision records the previous and new SHA-256 and the regions, never the hidden content. Playbook copies of the evidence (Milestone 5) must be redacted too.

## D-045 — Reordering sends the complete order

**Decision.** Reordering (buttons or Alt+↑/↓) sends the full list of step ids; the backend accepts it only if it is exactly the session's current set, then rewrites positions in one transaction and records a `reorder` decision. New steps are still appended at the end.
**Consequences.** Concurrent changes (for example a capture adding a screenshot) cannot silently drop or duplicate steps; the user is asked to refresh instead.

## D-046 — Playbook content is one validated JSON document with per-item provenance (Milestone 5)

**Decision.** A playbook's body is stored in `playbooks.content_json` as a versioned document (`schemaVersion` 1): purpose, scope, prerequisites, required permissions, numbered steps (title, instruction, command, expected result, note, screenshots), verification, warnings, troubleshooting and rollback. Rust validates it on every save (`deny_unknown_fields`, limits, unique ids, images must belong to the playbook). Every item records its origin: `session` (copied unchanged from an approved step, with the source session and step), `edited` (copied, then changed) or `authored` (written in the playbook). The editor switches `session` to `edited` on the first change.
**Consequences.** Recorded facts, edited copies and written instructions stay distinguishable in the editor and in exports. Future AI suggestions can get their own origin without a schema change.

## D-047 — Generation copies only approved steps and invents nothing

**Decision.** "Create playbook" turns each approved step into a numbered step (title, description as instruction, command for command steps, notes, screenshots) in timeline order. Rejected, excluded and pending steps are left out. Purpose, scope, expected results, verification, warnings, troubleshooting and rollback start empty; the verification section says that nothing was recorded automatically, and publishing reminds the author to describe real checks.
**Consequences.** A generated playbook never claims a verification result or expected outcome that nobody wrote down.

## D-048 — Evidence is copied into the playbook; redaction follows the copies

**Decision.** Screenshots of approved steps are copied (with their annotations) into `<workspace>/playbook-assets/<playbook_id>/` and recorded in `playbook_assets` with the source attachment and step. The `evidence` scheme serves these copies by id like attachments. Redacting a screenshot redacts every playbook copy of it the same way (new file, original copy deleted), and the result reports how many copies were redacted or failed.
**Consequences.** Deleting a session no longer breaks playbooks built from it, and published revisions keep their images. Sensitive content removed from evidence is also removed from playbooks.

## D-049 — Draft, review and publish; published revisions are immutable

**Decision.** Only drafts can be edited (autosaved). A draft can be submitted for review (editing locked) or published directly; a playbook in review can be returned to draft or published. Publishing requires at least one titled step and records an immutable revision (`playbook_revisions`: number, title, snapshot of metadata and content, note, author). "Edit as new draft" reopens a published playbook for the next version; earlier revisions stay unchanged. Evidence copies referenced by any revision are never removed by later edits.
**Consequences.** What was published can always be shown exactly as it was; revision history and comparison (Milestone 7) build on these snapshots.

## D-050 — Every export format is rendered in Rust from one document model (Milestone 6)

**Decision.** `src-tauri/src/export/` loads one playbook version into an `ExportDocument` (title, status line, metadata, content, evidence references, source session titles, notices) and renders it as Markdown (`markdown.rs`) or HTML (`html.rs`). PDF is not a third renderer: it is the HTML export printed by WebView2 (`pdf.rs`). Screenshots are prepared once (`images.rs`) for all formats.
**Consequences.** The formats cannot drift apart: the same sections, order, provenance and notices appear everywhere, and the PDF looks exactly like the HTML file. Revision comparison (Milestone 7) can reuse the same model.

## D-051 — Exports go to the workspace `exports` folder and never overwrite

**Decision.** Files are written to `<workspace>/exports/` with names built from an ASCII slug of the title, the version (`draft`, `review`, `r3`) and the local time, plus `-2`, `-3`… if a name exists. Markdown is a folder (`<name>/<slug>.md` + `images/`) assembled under a hidden temporary name and renamed when complete; HTML and PDF are single files written atomically (the PDF is renamed into place only after its `%PDF-` signature is checked). Temporary files are removed on failure. **Show in folder** (`reveal_export`) accepts only a relative path that resolves inside the exports folder and exists, and is implemented in Rust.
**Consequences.** No save dialog and no file-system permission for the webview; a failed export leaves nothing half-written; earlier exports are never replaced. Users copy files out of the exports folder to share them (shown in the dialog with its full path). A "save as" location chooser can be added later without changing the renderers.

## D-052 — Plain text stays literal in every format

**Decision.** Playbook text is plain text, so exports must not reinterpret it. Markdown backslash-escapes every character with inline meaning (`\ ` * _ [ ] < > | ~ # $`), entity-like `&…;`, and block markers at the start of a line (`-`, `+`, `=`, `1.`); leading indentation becomes non-breaking spaces; line breaks become hard breaks; commands use fences longer than any backtick run they contain. HTML escapes `& < > " '` and keeps line breaks with `white-space: pre-wrap`; commands are `<pre><code>`. The HTML file contains no script, embeds images as `data:` URIs and declares `default-src 'none'; img-src data:; style-src 'unsafe-inline'`.
**Consequences.** A step titled `<script>` or `**bold**` appears exactly as written; an exported HTML file cannot run code or contact a server when opened. Rich formatting inside playbook text is not supported (and not pretended).

## D-053 — PDF through WebView2 PrintToPdf in a hidden, isolated window

**Decision.** The PDF export writes the HTML to a temporary file, opens it in a new hidden WebView2 window (`visible(false)`, no taskbar entry, created from an async command), and calls `ICoreWebView2_7::PrintToPdf` when the page has loaded; the window is destroyed afterwards. A local file is a remote origin for Tauri, so that window cannot call any DevTrace command, and the document's CSP blocks scripts. Prints are serialized (one at a time) and time out after 120 s. Paper size follows the Windows region setting (Letter for US Letter/Legal regions, A4 elsewhere); the header shows the print date and title and the footer page numbers, with the file address suppressed. `webview2-com` must match the version wry uses, so Tauri is pinned to `~2.12`.
**Consequences.** No PDF library, no bundled browser and no new permissions; PDF output uses the same fonts and layout as the HTML export. Printing from a never-shown window was verified end to end (the E2E test opens the result with the Windows PDF renderer). PDF export is Windows-only in this version; other platforms report it as unavailable (`AppInfo.pdfExportSupported`).

## D-054 — What an export says about provenance and status

**Decision.** Every step states where it came from ("From session “X” (captured screenshot)", "…, edited after copying", or "Written in the playbook"), using the editor's vocabulary. Unpublished versions say so in the status line and a notice; an older revision says it is superseded; the current version of a playbook marked out of date says so with the note. Highlight boxes are drawn on a copy of the screenshot with numbers matching a caption list; redacted screenshots stay redacted and say so (copies made from redacted evidence now carry `redacted_at`). Missing image files are reported (in the result and at their place in the document) instead of failing the export. Empty sections are left out; warnings come before the steps, in the editor as well. The footer names the DevTrace version, export time, playbook id, and repeats that DevTrace never adds verification results.
**Consequences.** A reader of an exported file can tell recorded evidence from edited and written content, and an unpublished or outdated procedure cannot be mistaken for the current published one.

## D-055 — Which version is exported

**Decision.** The export dialog lists the unpublished working copy (for drafts and playbooks in review) followed by every published revision. A published playbook exports its newest revision by default (the immutable snapshot, not the working copy). Before exporting a draft, pending autosave changes are saved; if saving fails, the export is refused with an explanation.
**Consequences.** Published exports are reproducible from the stored revision; draft exports always contain what the editor shows.

## D-056 — Restoring a version never loses work (Milestone 7)

**Decision.** Restoring a published revision (or a saved draft) replaces only the working copy, which becomes a draft. If the working copy differs from the newest published revision, it is first stored as a **restore point** (`playbook_restore_points`: the same snapshot shape as a revision, plus what replaced it); restore points can be read, compared and restored in turn. Restoring is refused while the playbook is in review and when the working copy already matches the chosen version. `playbooks.restored_from_revision` tells the editor that the draft started from an older revision until the next publication. Evidence copies referenced by restore points are kept like those referenced by revisions.
**Consequences.** Published revisions are never modified, and unpublished drafts survive a restore. Restore points accumulate with each restore that replaces unpublished work; they are deleted only with their playbook.

## D-057 — Versions are compared as canonical plain text

**Decision.** The version history page compares any two versions (working copy, revisions, saved drafts) with the existing line diff: each version is rendered as plain text — metadata, then every section in document order with provenance suffixes, commands indented, and each screenshot as one line (size, short id, redacted, number of highlights). Long runs of unchanged lines are collapsed to three lines of context (a switch shows every line). Revisions and saved drafts are read through dedicated commands; the comparison runs in the webview.
**Consequences.** Text, metadata and screenshot changes (including a later redaction) are visible as added/removed lines with `+`/`−` signs and screen-reader text, never by color alone. Pixel-level image differences are not shown.

## D-058 — "Out of date" is an explicit, reversible marker

**Decision.** A playbook with at least one published revision can be marked out of date with an optional note (what changed), and marked current again. The marker appears in the editor, the Playbooks list, the Knowledge Library (with a freshness filter) and in exports of the current version; publishing a new revision clears it.
**Consequences.** Readers are warned before following a procedure that no longer matches the systems it describes, without hiding or deleting it. Drafts that were never published cannot be marked.

## D-059 — Duplicates are independent drafts that remember their origin

**Decision.** "Duplicate" copies the working copy or a chosen revision into a new draft titled "Copy of …": metadata and content are copied (step provenance and source-session links included), every referenced screenshot gets its own file and row in the new playbook's folder, and `based_on_playbook_id` / `based_on_revision` record the origin (the link becomes empty if the original is deleted). The author is the current author name when set.
**Consequences.** A verified procedure can be adapted for another environment without touching the original or its revisions; deleting either playbook never breaks the other.

## D-060 — The Knowledge Library lists published versions

**Decision.** The library's default filter shows playbooks with at least one published revision, whatever the state of their working copy; other filters select by working-copy status. A Revision column shows how many revisions exist.
**Consequences.** A procedure that is being revised ("Edit as new draft", or after a restore) stays findable as the reusable reference it was published as.

## D-061 — Automatic capture reacts to visible changes, never to input (Milestone 8)

**Decision.** "Improved click detection" is implemented without any keyboard, mouse or accessibility hook. Automatic capture is opt-in per capture (off by default, switchable while recording): about once a second the chosen target is captured into a 96×64 grayscale sample kept only in memory; when more than 2 % of the sample changed compared with the last screenshot and the screen has settled (two still samples), a normal screenshot is taken with trigger `auto`. Screenshots are at least 3 s apart and at most 12 per minute; nothing is sampled while paused; three failures in a row switch it off with an explanation. Automatic screenshots are added to the step list without being selected.
**Consequences.** DevTrace notices dialogs, page changes and command results that change the screen, but not clicks that change nothing visible, and it cannot know which control was clicked. Typing in a field and blinking cursors stay below the threshold. Privacy stays as before: only the chosen target is read, only while recording, and the samples are discarded.

## D-062 — Terminal logs are written by the user's own terminal into the workspace

**Decision.** DevTrace never starts, attaches to or injects into a terminal. `Start terminal log` creates an empty file in `terminal-logs/<session>/` and shows how to write to it: `Start-Transcript -Path "<file>" -Append` for PowerShell (copyable), or the path for PuTTY and other tools that log to a file. A reader thread reads only what is appended to that file (BOM-aware for UTF-8 and UTF-16) while logging is on. Format adapters (`TranscriptParser`) turn lines into steps: the PowerShell adapter skips the framed header and footer blocks and pairs prompt lines with their output; the plain adapter groups output between pauses of 2.5 s.
**Consequences.** The user sees and controls exactly which terminal is logged and stops it there (`Stop-Transcript`) and in DevTrace. Only files DevTrace created are read. New formats are new adapters. Prompts that do not look like `PS …>` are recorded as output, not commands.

## D-063 — Secret-looking values are masked before terminal text is stored

**Decision.** Before a recorded command or output is stored, values following secret-looking keys (`password`, `passwd`, `pwd`, `passphrase`, `secret`, `token`, `apikey`, `api_key`, `access_key`, `private_key`, `client_secret`, as `key=value`, `key: value` or `-key value`) and `Bearer`/`Basic` credentials are replaced with `********`; steps record whether anything was masked. The raw log file in the workspace is not modified.
**Consequences.** Common accidental leaks do not reach steps, playbooks or exports. Masking is a safety net, not a guarantee (a secret printed without a recognizable key is kept), which the UI and README say; every recorded step still needs review, and screenshots can be redacted. Users who need the raw log can open the file; deleting the session deletes it.

## D-064 — Watched files are chosen in the system dialog from Rust

**Decision.** The dialog plugin is used only from Rust; the webview has no dialog or file-system permission and never supplies a path. `Watch a file…` asks the backend, which shows the system's open dialog, accepts text files up to 1 MB, and polls size and modification time every second (no OS file-notification API, which is unreliable for editors that replace files). A change is read after one more unchanged check. For automated tests only, `DEVTRACE_E2E_PICK_FILE` names the file instead of showing the dialog; it is set by the end-to-end test together with an isolated workspace and gives no access beyond what the launching user already has.
**Consequences.** Only files the user explicitly picked are read, and only while watched (at most 5 per session, stopped with the session). Changes faster than about two seconds are merged into one. Binary files and very large files are refused with an explanation.

## D-065 — Change records keep evidence, review and verification apart

**Decision.** Every change record states how it is known (`observed` by DevTrace from a watched file, `declared` by a person, or `verified`), separately from its review (`pending` / `approved` / `rejected` with reviewer, time and comment). Verifying requires a note saying how the outcome was checked and is refused for rejected changes; verified changes cannot be rejected; only declared, pending changes can be edited, and observed values never. A watched-file change is stored atomically as a session step (changed lines) plus an observed change record (full before and after text) linked by `event_id`.
**Consequences.** DevTrace never presents something it saw as a confirmed or verified change. The change history shows who approved and who verified what, and links back to the evidence. Deleting a session keeps its change records (unlinked).

## D-066 — New event types and sources without a migration

**Decision.** Terminal output (`log`), file changes (`change`) and the sources `terminal` and `file_watch` were added to the Rust enums; `events.event_type` and `events.source` have no SQL `CHECK`, so no migration was needed. These types can only be recorded by integrations (`create_event` refuses them); the schema change of this milestone (v6) only extends `change_records`.
**Consequences.** Older DevTrace versions refuse to open a v6 database anyway (newer-version protection), so they never meet the new values. Playbook generation treats recorded commands and terminal output like other approved steps with code.

## D-067 — Workspace backups are one verified zip; restoring never overwrites in place (Milestone 9)

**Decision.** **Back up workspace…** writes one zip file where the user chooses (system save dialog, from Rust): a `VACUUM INTO` copy of the database, `attachments/`, `playbook-assets/` and `terminal-logs/`, and `manifest.json` (format version, app and schema versions, counts, size and SHA-256 of every file). Exports, earlier backups and crash reports are left out. The archive is written to `<name>.partial` and renamed when complete; saving into the backed-up folders is refused, and so is backing up during a capture. **Restore from backup…** validates the archive before showing it (format, versions, every entry name confined to the known folders, sizes, no unlisted, encrypted or symbolic-link entries), and only after confirmation extracts it into `backups/restore-staging-<time>/`, verifying every checksum and `PRAGMA integrity_check`. Then, holding the database lock, it closes the connection, moves the current data to `backups/before-restore-<time>/`, moves the staged data into place and reopens (and if needed migrates) the database; any failure moves everything back. Terminal logs and watched files are stopped first, and the interface reloads afterwards.
**Consequences.** A damaged, tampered, foreign or newer backup cannot replace a working workspace. The replaced data is always kept (never deleted automatically), so a restore can be undone by hand. Backups from older versions are upgraded on restore. Restoring needs free disk space for the staged copy. The zip format (deflate) can be opened with standard tools.

## D-068 — Application commands are allowed per window through the app manifest

**Decision.** `build.rs` lists every application command in Tauri's app manifest, which generates an `allow-<command>` permission for each and denies commands no capability grants. The `main-window` capability allows exactly those commands (plus core window permissions) for the window `main` only. `scripts/check-permissions.mjs` (run by `npm run lint`) fails when the handlers in `lib.rs`, the manifest and the capability differ; the end-to-end test checks that plugin commands (file dialog, opener) are refused to the webview.
**Consequences.** A new command does nothing until it is deliberately listed and allowed; any other webview (such as the hidden PDF window) gets no command access. The generated permission files are build output (`src-tauri/permissions/autogenerated`, ignored by Git).

## D-069 — Crash reports stay on the computer

**Decision.** Release builds abort on panic and have no console. A panic hook writes the message, the source location and a backtrace to `<workspace>/logs/crash-<time>.txt` before the process ends; nothing is sent anywhere. In the interface, a React error boundary replaces a crashed window with an explanation, the error message and a Reload button.
**Consequences.** Failures leave a trace the user can inspect and choose to share, without telemetry. Reports contain no workspace content, but stripped release binaries give backtraces without symbol names; the message and location remain useful.

## D-070 — No automatic updater

**Decision.** DevTrace does not check for or download updates. Users update by installing a newer installer over the old one (documented in [INSTALL.md](INSTALL.md), with a backup first); the database is upgraded on first start after a pre-migration copy. Tauri's updater plugin was not added: it would need network access, an update server and signing keys, contrary to the local-first, no-network posture.
**Consequences.** Users decide when to update and nothing contacts the network. Organizations deploy the MSI with their usual tools. A future opt-in updater would need its own decision (signed manifests, explicit consent, visible checks).

## D-071 — Accessibility is audited automatically on every screenshot

**Decision.** The end-to-end test runs axe-core (WCAG 2.0/2.1 A and AA rules) on every screen it photographs, in both themes, through the DevTools protocol (the app's CSP is not relaxed), and fails on serious or critical violations. The first audits found low-contrast informational text using the tertiary color; the specification's light secondary text color #6E6E73 falling short of 4.5:1 on the specification's own secondary surface (#F0F0F2, 4.45:1), on selected rows (4.46:1) and on the screenshot viewer (4.15:1); white annotation labels on the highlight blue (4.0:1); scrollable areas not reachable by keyboard; a link distinguished by color only; `aria-label` on elements that cannot be named; and a capture status link whose name did not contain its visible text. Fixes: informational text uses the secondary color (tertiary stays for placeholders and disabled text); the light secondary text token is darkened to **#636368** (5.25:1 on #F0F0F2, visually almost identical — the only deviation from the specification palette); annotation labels use the darker accent fill; focusable, named scroll containers; underlined inline links; groups instead of named `code`/`pre` elements; the visible status in the link's name.
**Consequences.** Regressions in contrast, names and keyboard access on the audited screens fail the build. Automated checks do not replace manual testing with screen readers, which has not been done for this version.

## D-072 — Installers are built but not signed in this repository

**Decision.** `npm run tauri build` produces an NSIS installer (per-user, no administrator rights) and an MSI (per-machine, for managed deployment). They are not code-signed: no certificate is available to this project. [INSTALL.md](INSTALL.md) explains the SmartScreen warning, checksum verification, and the `certificateThumbprint` / `signCommand` settings for signing.
**Consequences.** Users of unsigned builds see SmartScreen warnings and some organizations will block them; maintainers should sign release builds. Running the installers was not exercised in the automated tests (it would modify the test machine); the release executable and the executable extracted from the MSI by an administrative extraction (`msiexec /a`, which installs nothing) both passed the full end-to-end test.
